# Pipeline_Krestiki_Noliki.md — Tic-Tac-Toe v1

> Рабочий pipeline для OpenCode.
>
> Главная цель: последовательно собрать мобильную HTML5-игру «Крестики-нолики» на TypeScript + Vite + Canvas 2D с HTML/SVG UI, не допуская преждевременного усложнения архитектуры.
>
> Проект должен быть пригоден для дальнейшей упаковки/адаптации под Yandex Games и Android, но интеграции конкретных платформ не реализуются раньше соответствующих этапов.

# 1. Цель продукта

Создать небольшую, цельную и приятную игру в классические крестики-нолики, в которой:

- можно играть против другого человека на одном устройстве;
- можно играть против AI на 4 уровнях сложности;
- можно включать таймер на ход с пресетами `5 / 10 / 30 секунд` или играть без таймера;
- можно играть одиночную партию либо серию `Best of 3 / Best of 5` — в PvP и PvE;
- есть статистика и достижения;
- достижения воспринимаются как заметная награда, а не как сухое уведомление;
- есть разблокировка косметики через Achievement Score;
- есть уютный cozy-fantasy визуальный стиль с тёплыми мягкими цветами;
- игра прежде всего рассчитана на телефон в portrait, но корректно работает и в landscape;
- игровая сцена работает на Canvas 2D;
- UI и иконки реализуются HTML/CSS/SVG;
- игра может развиваться дальше без переписывания игрового ядра.

# 2. Технологический baseline

## Обязательный стек

- TypeScript
- Vite
- Vitest — тесты критической игровой логики
- HTML5 Canvas 2D для игровой сцены
- HTML/CSS для интерфейса
- SVG/HTML для UI-иконок и элементов, где это рациональнее Canvas
- Browser APIs без лишних библиотек там, где нативных возможностей достаточно

## По умолчанию не использовать

- Unity
- Unreal Engine
- Phaser
- React/Vue/Svelte
- UI-framework только ради кнопок/меню
- state-management библиотеку
- animation framework
- audio framework
- отдельную библиотеку для таймера
- отдельную библиотеку для хранения данных

Каждая новая зависимость требует конкретного обоснования в контексте существующего кода. Формулировка «может пригодиться позже» не является основанием.

# 3. Целевая структура ответственности

Не требовать заранее фиксированного количества файлов.

Минимальные смысловые границы проекта:

```text
Game Core
  ↓
Renderer
  ↓
UI
  ↓
Persistence
  ↓
Platform integration
```

При этом новая папка, класс, интерфейс, сервис или менеджер создаётся только тогда, когда текущий код реально требует такого разделения.

Пример допустимого роста:

```text
src/
├── game/
├── ai/
├── rendering/
├── ui/
└── main.ts
```

Если для текущего этапа достаточно меньшего количества файлов — использовать меньше.

Не создавать заранее:

- `Factory` ради одной реализации;
- `Provider` ради одного источника;
- `Manager` без реально нескольких независимых обязанностей;
- `Strategy` без нескольких реально различающихся стратегий;
- `Adapter` до появления второй стороны адаптации;
- отдельную конфигурационную систему без потребности;
- абстракции «на будущее».

# 4. Главный принцип разработки: Ponytail / YAGNI

Использовать принципы Ponytail как постоянное инженерное правило.

Лестница решения:

```text
1. Это вообще должно существовать?              → нет → не писать
2. Это уже есть в проекте?                      → переиспользовать
3. Это умеет стандартная библиотека/API?        → использовать
4. Это умеет браузер/платформа нативно?          → использовать
5. Это умеет уже установленная зависимость?     → использовать
6. Это можно выразить одной простой строкой?    → не создавать систему
7. И только потом — написать минимальное решение
```

Критически важно: принцип «лень» применяется к решению, а не к анализу.

Перед изменением агент обязан:

1. прочитать затрагиваемый код;
2. проследить реальный поток данных/состояния;
3. найти уже существующую реализацию;
4. только после этого выбрать минимальный способ решения.

Нельзя экономить кодом за счёт:

- валидации;
- корректного состояния игры;
- защиты от потери данных;
- обработки ошибок;
- accessibility;
- mobile usability;
- корректного ввода;
- тестируемости критической игровой логики.

Официальный Ponytail описывает именно такую последовательность и отдельно оговаривает, что минимальность не должна достигаться за счёт безопасности, обработки ошибок или accessibility.

---

# 5. Правило «не строить будущее вместо настоящего»

Будущая поддержка Yandex Games и Android учитывается в архитектурных границах, но не реализуется заранее.

Допустимо заранее:

- держать игровое ядро независимым от DOM и Canvas;
- не привязывать игровую логику к Yandex SDK;
- использовать browser APIs в отдельном от ядра месте;
- хранить настройки/прогресс в локальном хранилище через минимальный слой;
- писать код так, чтобы Canvas не был единственным источником состояния.

Не делать заранее:

- Yandex SDK integration;
- Yandex leaderboards;
- Yandex ads;
- Yandex player account;
- Android bridge;
- Capacitor configuration;
- cloud saves;
- online multiplayer.

Платформенная интеграция начинается только на соответствующем этапе pipeline.

# 6. Принцип изменения: одна задача → один законченный результат

Каждый этап должен иметь:

1. чёткий результат;
2. минимальный набор изменений;
3. автоматические тесты там, где они оправданы;
4. ручную проверку там, где автоматизация не заменяет реальный UX;
5. overengineering review;
6. контрольную точку.

После прохождения этапа агент должен остановиться.

Нельзя автоматически переходить к следующему этапу только потому, что текущая задача закончена.

# 7. STOP CONDITION

После каждого этапа:

```text
IMPLEMENT
↓
TEST
↓
VERIFY
↓
OVERENGINEERING REVIEW
↓
CLEAN UP
↓
STOP
```

Если критерии выхода не выполнены — следующий этап запрещён.

Если критерии выполнены — агент сообщает краткий итог и ждёт следующую задачу/разрешение продолжить.

# 8. Правила работы OpenCode

## Сводный алгоритм на каждый этап

1. Понять задачу — прочитать относящиеся разделы GDD, раздел текущего этапа, код и `package.json`.
2. Определить минимум — какие файлы реально менять; новая зависимость только с обоснованием (§4).
3. Реализовать — строго в рамках этапа, без кода «на будущее».
4. Протестировать — автотесты критической логики (§10) + ручная проверка того, что нельзя покрыть тестами.
5. Проверить качество — сборка, TypeScript, тесты, консоль, мобильный вид.
6. Аудит на лишнее — ворота O1–O8 (§9).
7. Отчитаться и STOP (§7) — к следующему этапу только после подтверждения.

Расхождения GDD/кода не додумывать — остановиться и спросить. Полезное вне этапа — в `BACKLOG.md` (§32).

## Перед каждым этапом

Агент должен:

- прочитать `GDD_Krestiki_Noliki_v1.md` в части, относящейся к этапу;
- прочитать текущую реализацию;
- проверить `package.json`, конфигурацию и доступные зависимости;
- понять текущий путь пользовательского действия;
- определить, какие минимальные файлы действительно нужно менять.

## Во время реализации

- не менять несвязанные части проекта;
- не делать массовый рефакторинг «заодно»;
- не переименовывать всё ради красоты;
- не устанавливать зависимости без необходимости;
- не создавать код для функций будущей версии;
- не дублировать существующие функции;
- не превращать простую задачу в архитектурную систему.

## После реализации

Проверить:

- сборку;
- тесты;
- ошибки TypeScript;
- поведение на мобильном размере экрана;
- отсутствие очевидного регресса;
- overengineering.

# 9. Anti-overengineering Gates

После каждого крупного этапа пройти следующий короткий аудит.

## O1 — YAGNI

Есть ли новый код, который не нужен текущей версии?

Если да — удалить.

## O2 — Reuse

Есть ли в кодовой базе уже решение этой задачи?

Если да — переиспользовать.

## O3 — Abstraction

Появилась ли абстракция, потому что «когда-нибудь будет нужно»?

Если да — убрать, пока не появилась реальная вторая реализация/необходимость.

## O4 — Dependencies

Добавлена ли библиотека там, где достаточно Canvas API / DOM / CSS / Web APIs / TypeScript?

Если да — удалить зависимость и упростить решение, если функциональность не теряется.

## O5 — File explosion

Не создано ли несколько файлов там, где одной простой реализации было бы достаточно?

Если да — объединить.

## O6 — Manager/Factory/Provider test

Каждый новый `Manager`, `Factory`, `Provider`, `Service`, `Adapter`, `Strategy` должен иметь объяснимую текущую причину существования.

Если объяснение — только «для масштабируемости» → удалить.

## O7 — Dead code

Удалить:

- unused imports;
- unused functions;
- unused types;
- unused constants;
- пустые или неиспользуемые обёртки;
- временные костыли, которые больше не нужны.

## O8 — Complexity vs benefit

Можно ли выполнить то же самое меньшим количеством движущихся частей без потери качества?

Если да — выбрать более простой вариант.

# 10. Обязательное правило тестирования

Тестировать в первую очередь **правила игры**, а не декоративную реализацию.

## Автоматически тестировать

- постановку фигуры;
- запрет хода в занятую клетку;
- правильную смену хода;
- победу X;
- победу O;
- ничью;
- невозможность продолжить игру после окончания партии;
- корректность определения победной линии;
- выбор хода AI;
- обязательную блокировку очевидной угрозы на Medium+;
- невозможность победить Impossible при корректном minimax;
- корректность timeout;
- результат серии Best of 3 / Best of 5;
- сохранение и загрузку прогресса;
- выдачу достижений;
- начисление Achievement Score;
- разблокировку косметики.

## Не обязательно писать отдельные unit-тесты для

- каждого CSS-класса;
- каждой декоративной анимации;
- каждой SVG-иконки;
- каждой функции рисования одного штриха;
- каждой кнопки отдельно, если поведение покрывается интеграционной проверкой экрана.

# 11. Mobile-first правила

Целевая платформа разработки — браузер с приоритетом мобильного телефона.

## Layout

- Portrait — основной режим.
- Landscape — поддерживаемый режим.
- Интерфейс должен корректно переживать изменение размеров viewport.
- Не допускать горизонтального overflow.
- Игровое поле всегда остаётся очевидно интерактивным.
- Нажатия пальцем должны попадать в клетки с разумным запасом.
- Кнопки должны быть пригодны для пальца, а не только для мыши.

## Input

Использовать Pointer Events как единый механизм ввода, если текущая реализация не даёт конкретной причины использовать другое решение.

Не привязывать игровую логику непосредственно к `click`/`touchstart`.

Поток должен быть примерно таким:

```text
Pointer input
↓
координаты
↓
определение клетки
↓
Game Core
↓
новое состояние
↓
Renderer/UI
```

## Canvas quality

Учитывать:

- CSS size;
- внутренний pixel size;
- `devicePixelRatio`;
- изменение viewport;
- изменение ориентации.

Цель — чёткая графика без размытых линий на современных мобильных дисплеях.

# 16. Этап 4 — PvE и AI

## Цель

Добавить четыре уровня сложности без четырёх независимых архитектурных подсистем.

## Уровни

### Easy

- AI допускает заметные ошибки;
- может выбирать далеко не оптимальный ход;
- не обязан играть идеально.

### Medium

- выигрывает при наличии немедленной возможности;
- блокирует очевидную угрозу;
- умеет делать базовый разумный выбор;
- может допускать стратегические ошибки.

### Hard

- тот же minimax, что и Impossible;
- около 15% ходов AI выбирает не лучший, но разумный ход;
- сильный, но проходимый уровень.

### Impossible

- тот же принцип совершенной игры: AI всегда выбирает лучший ход;
- при равноценных ходах допускается рандомизация выбора, чтобы партии не выглядели идентичными;
- рандомизация не должна превращать обязательное выигрышное решение в ошибку.

## Важное ограничение

Не создавать 4 полностью независимых AI-модуля только ради названий уровней.

Все уровни выражаются одной системой оценки/выбора хода: уровень задаёт вероятность отклониться от лучшего хода.

Стартовые значения (можно настроить при балансе):

- Easy — часто ошибается, иногда пропускает выигрыш и угрозу (≈60%);
- Medium — всегда берёт немедленный выигрыш и блокирует немедленную угрозу, в остальном часто ошибается (≈30%);
- Hard — редко отклоняется от лучшего хода (≈15%);
- Impossible — никогда (0%).

## Tests

Обязательны сценарии:

- AI выбирает немедленную победу (Medium и выше);
- AI блокирует немедленную победу игрока на требуемых уровнях (Medium и выше);
- Hard иногда отклоняется от лучшего хода, но в целом играет сильно;
- Impossible не проигрывает при полном переборе корректных состояний;
- равноценные ходы могут различаться по выбору.

### STOP

# 17. Этап 5 — Таймер

## Цель

Добавить один универсальный тип таймера на ход.

## Пресеты

- без таймера;
- 5 секунд;
- 10 секунд;
- 30 секунд.

## Правило timeout

**Истечение времени = поражение текущей партии.**

Не пропускать ход автоматически.

Не продолжать отсчёт после окончания партии.

Не вести отсчёт на ходу AI — таймер действует только на ход человека.

Не вести отсчёт на экранах результата и во время показа наград.

Не позволять двойному срабатыванию timeout.

## UI

- крупный и читаемый таймер;
- понятная связь таймера с текущим игроком;
- последние секунды визуально подчёркиваются без агрессивного мельтешения;
- звук тиканья/сигнала допустим позже на этапе polish.

## Tests

- timeout на ходу X;
- timeout на ходу O;
- новый раунд сбрасывает таймер;
- отсчёт не идёт на ходу AI;
- изменение режима таймера корректно применяется;
- завершённая партия не вызывает timeout.

### STOP

---

# 18. Этап 6 — Состояние игры и сохранение

## Цель

Сохранять только тот прогресс, который действительно нужен первой версии.

## Минимум

Сохранять:

- настройки пользователя;
- выбранные косметические предметы;
- статистику;
- разблокировки;
- Achievement Score.

Не требуется на первом проходе сохранять незавершённую партию, если GDD этого не требует.

Перезагрузка посреди партии или серии — возврат в главное меню; сохранённая статистика и прогресс при этом не теряются.

## Storage

Начать с browser storage.

Не создавать полноценный storage framework без реальной потребности.

Обязательно обработать:

- отсутствие данных;
- повреждённые/невалидные данные;
- версию сохранения;
- безопасный fallback к значениям по умолчанию.

### STOP

# 20. Этап 8 — Achievement System

## Цель

Создать лёгкую мета-прогрессию, которая мотивирует сыграть ещё одну партию.

## Базовые достижения

Примеры:

- первая победа;
- выигрышная серия;
- победа над определённой сложностью;
- несколько ничьих;
- победа за малое количество ходов;
- достижение, связанное с таймером;
- достижения за количество сыгранных партий.

Точные числа фиксируются в GDD/конфигурации после определения баланса.

## Achievement Score

Каждое достижение может давать Achievement Score.

Score — **прогресс**, а не внутриигровая денежная валюта.

Использование Score:

- постепенное открытие косметических тем;
- открытие дополнительных наборов фигур.

Не добавлять магазин, цены, экономику и микротранзакции.

## Критически важное UX-требование

**Получение достижения должно быть заметным событием, а не сухим уведомлением.**

При разблокировке:

- яркая, но короткая анимация;
- красивая иконка;
- название достижения;
- понятное сообщение о награде;
- Achievement Score;
- приятный звук;
- возможность быстро закрыть/продолжить игру.

Вдохновение по ощущению награды — WoW: достижение должно ощущаться как момент прогресса и признания, а не как строка в логе.

При этом не копировать визуальный стиль или графические ассеты WoW.

## Tests

- достижение выдаётся ровно один раз;
- повторная проверка не дублирует награду;
- Score начисляется корректно;
- вычисление порога разблокировки корректно (первый реальный предмет — Набор 2, P2);
- сохранение переживает перезапуск страницы.

### STOP

# 26. Overengineering Audit перед релизом

Перед выпуском выполнить полный аудит репозитория.

Искать:

- преждевременные абстракции;
- лишние зависимости;
- лишние файлы;
- лишние конфиги;
- дублирующиеся helper-функции;
- мёртвый код;
- комментарии, описывающие очевидное;
- платформенный код, который пока нигде не используется;
- feature flags без реальной нужды;
- неиспользуемые настройки;
- код «на будущее».

Для каждого найденного элемента:

```text
нужен сейчас?
 ├─ да → оставить
 └─ нет → удалить
```

Но не удалять код только ради сокращения строк, если он нужен для:

- валидации;
- устойчивости;
- безопасности;
- accessibility;
- сохранности данных;
- тестируемости.

# 32. Как агент должен предлагать изменение вне текущей задачи

Если во время работы обнаружена полезная, но не относящаяся к текущему этапу функция:

1. не реализовывать её автоматически;
2. кратко зафиксировать предложение;
3. при наличии `BACKLOG.md` добавить одну короткую запись;
4. продолжить текущую задачу.

Исключение — исправление критической ошибки/безопасности/потери данных, которая непосредственно мешает текущему сценарию.

# 33. Как агент должен писать код

Приоритет:

```text
понятно
↓
корректно
↓
тестируемо
↓
минимально
```

Не приоритет:

```text
абстрактно
↓
универсально
↓
«enterprise-ready»
```

Комментарии писать только там, где они объясняют:

- неочевидное ограничение;
- причину нестандартного решения;
- важный edge case;
- внешнее ограничение платформы.

Не комментировать очевидный код словами, которые просто повторяют его.

# 34. Правило для архитектурных сомнений

Если агент сомневается между:

### A
простым локальным решением;

### B
новой абстракцией;

сначала выбирать A.

Переход к B допустим, если существует хотя бы одна конкретная текущая причина:

- несколько реальных реализаций уже есть;
- текущий код стал труден для изменения именно из-за отсутствия разделения;
- тестирование реально требует границы;
- платформенная интеграция действительно появилась;
- повторение кода стало существенным.

Фраза «это лучше масштабируется» сама по себе недостаточна.

- Achievement System не должна управлять игровой логикой;
- Yandex integration не должна менять PvP/PvE engine.

# 39. Важное правило для AI-агента

**Не пытайся закончить всю игру за один ответ.**

Всегда работай в пределах текущего этапа.

Если этап требует изменения 2 файлов — не создавать 12 файлов «для порядка».

Если нативный браузерный API решает задачу — не устанавливать библиотеку.

Если существующая функция подходит — не создавать вторую.

Если задача уже решена — не рефакторить её без причины.

Если feature не входит в текущий этап — не реализовывать её.

Если решение достаточно простое — оставить его простым.

Но:

**не жертвовать корректностью, сохранением данных, обработкой ошибок, безопасностью, accessibility и мобильным UX ради сокращения кода.**

# 40. Режимы упрощения для OpenCode

Принципы Ponytail (см. §4) используются как поддерживающий инженерный механизм, а не как замена здравому смыслу. Внешний плагин для этого не требуется.

Рекомендуемый подход:

- обычная разработка — постоянно следовать лестнице решения из §4;
- локальный overengineering review — короткий аудит по воротам O1–O8 из §9;
- релизный аудит репозитория — чек-лист из §26;
- упрощение «ultra» — только для отдельного удаления/упрощения, когда есть основания считать участок явно переусложнённым.

После каждого крупного этапа можно пройти review, но не превращать review в бесконечную бюрократию.

# 41. Критерий успеха Pipeline

Pipeline успешен, если по его завершении:

1. игрок получает цельную и приятную игру;
2. игровой engine прост и понятен;
3. визуальная часть выглядит заметно лучше голого прототипа;
4. mobile UX не является компромиссом;
5. будущая адаптация под платформы возможна;
6. код не содержит архитектуры ради архитектуры;
7. новые возможности можно добавлять постепенно;
8. OpenCode не расползается за пределы поставленной задачи.

Главный принцип проекта:

> **Простая игра должна оставаться простой внутри, даже если снаружи она становится богаче.**
