### T3. Модель ошибок Hard (P1, техническое — решение агента)

**Files:** `src/ai/ai.ts`, `src/ai/ai.test.ts`

Проблема: при «ошибке» (15%) Hard берёт **случайный** ход среди всех худших — включая откровенно провальные.

Изменение (только Hard; Easy/Medium/Impossible не трогаем — YAGNI):

- при срабатывании ошибки Hard выбирает **сильнейший из неточных ходов**: максимум `score` среди ходов с `score !== bestScore`; при равенстве — случайный из них (`pickCell`).
- Логика `protectImmediate` и шансы ошибок (60/30/15/0%) не меняются.

Почему не «фильтровать все проигрывающие ходы»: в ничьих позициях любая ошибка — это уже проигрыш; такой фильтр сделал бы Hard непобедимым и сломал ачивку «Тактическое превосходство» (победа над Hard). Сильнейший неточный ход убирает случайный мусор, но сохраняет стратегические ошибки → Hard остаётся проходимым.

Замечание (честно): правило «ошибка не должна отдавать немедленную победу сопернику», обещанное в обсуждении, в крестиках-ноликах эквивалентно уже существующей защите `protectImmediate` (ход не может создать сопернику немедленный выигрыш — только не заблокировать существующий). Работающее изменение — именно выбор сильнейшего неточного хода.

Тесты:

1. При вынужденной ошибке Hard возвращает **не худший, а сильнейший** из неточных (контролируемый `random`).
2. В позиции, где лучший ход — ничья, ошибка Hard ведёт к проигрышной линии (т.е. ачивку «Тактическое превосходство» по-прежнему можно получить).
3. Вилка: в позиции с двумя угрозами соперника ответ Hard — блок (защита не сломана), а в позиции, где у Hard есть выигрыш, он его не пропускает.
4. Easy по-прежнему может пропустить угрозу (без фильтра); Medium всегда блокирует/выигрывает немедленно.

**Verify:** прогон 20 партий Hard > Easy (существующий тест); live-партии: Hard не «висит» под немедленным выигрышем, но проигрывает при корректной игре игрока.

### T4. Canvas учитывает prefers-reduced-motion (P2, техническое)

**Files:** `src/main.ts`, при необходимости `src/rendering/boardRenderer.ts`

- Определять системную настройку `prefers-reduced-motion: reduce` (`window.matchMedia`) в момент запуска анимации знака и победной линии.
- При включённой настройке: **не запускать** `markAnim`/`winAnim` — отрисовать сразу конечное состояние (знак во весь размер, линия полностью). `drawBoard` уже умеет рисовать финальное состояние (`anim == null`, `winProgress ?? 1`).
- Звук, плашка результата, карточки достижений, статусы — работают как раньше (CSS-анимации уже отключаются `@media (prefers-reduced-motion)`).
- Учитывать смену настройки «на лету»: читать `matchMedia` при каждом старте анимации, не кэшировать на весь жизненный цикл (это же отвечает на проверку изменения предпочтения).
- Тесты: по §10 анимации — декоративные, unit-тест не обязателен; если окружение Vitest позволяет подменить `matchMedia` — добавить маленький тест решения, иначе live-проверка с честной пометкой в PROGRESS (в окружении агента нет эмуляции media-состояния — известное ограничение, BACKLOG).

**Verify:** при активной настройке знак и линия появляются мгновенно, звук и результаты не меняются; при выключённой — анимации как раньше. Закрыть пункт BACKLOG про canvas-анимации.

### T5. Набор 2 — реально применяемый (P1, продуктовое + UI)

**Files:** `src/rendering/boardRenderer.ts` (+тесты), `src/persistence/storage.ts` (+тесты), `src/main.ts`, `index.html`, `GDD_Krestiki_Noliki_v1.md` (§15.1, §19.5)

Что рисуем (всё кодом, без ассетов — решение Олега 01.10.2026):

- **Набор 1** (текущий, без изменений): X — мягкие изогнутые штриха «от руки», O — кольцо.
- **Набор 2** (новый, «руны»): X — прямые угловатые штрихи с лёгкими засечками, O — двойное кольцо. Знак занимает ~52% клетки, не касается сетки (те же инварианты, что у набора 1). Цвета не меняются (сино-стальной X, терракота O) — GDD §15.2.

Реализация:

- `boardRenderer.ts`: тип `MarkSet = 'set-1' | 'set-2'`; `markStrokes(mark, cx, cy, size, set)` (default `'set-1'` — существующие вызовы и тесты не ломаются); `drawBoard` пробрасывает набор.
- `storage.ts`: в `GameSettings` поле `markSet`; нормализация: отсутствует/невалидное → `'set-1'` (поштучный fallback, как у остальных полей); версия сохранения остаётся `1` (поле аддитивное).
- `index.html` (экран «Настройки», после fieldset «Звук»): fieldset «Набор фигур» с радиокнопками «Набор 1» / «Набор 2».
- Блокировка: при `achievementScore < 50` — «Набор 2» отключён, в подписи «откроется при 50 очках»; при ≥ 50 — доступен. Состояние читается при открытии экрана настроек.
- Выбор запоминается в настройках и применяется к следующей отрисовке поля.
- GDD §15.1/§19.5: заметка «Набор 2 реализован 09.10.2026 (этап v1.0.1), выбор — в настройках».
- Приёмка: Score только растёт, поэтому «выбран Набор 2 при Score < 50» невозможно без ручной правки localStorage; кросс-проверку не добавляем (YAGNI).

Тесты: геометрия набора 2 (отдельность штрихов, вписанность, отсутствие касания сетки — по образцу существующих `markStrokes`-тестов); fallback `markSet` в `storage.test.ts` (нет поля / мусор → `'set-1'`).

**Verify:** набрать 50 очков → уведомление → в настройках выбрать «Набор 2» → поле рисует новые знаки; перезагрузка сохраняет выбор; до 50 очков выбор закрыт с подписью.
